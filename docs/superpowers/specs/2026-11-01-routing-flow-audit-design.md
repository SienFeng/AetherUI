# 分流规则后台持续审计 设计

日期：2026-11-01
前置：`docs/superpowers/specs/2026-11-01-routing-flow-verification-design.md`（按需验证，已实现）。本文在其之上增加两件事，并补一个界面展示。

## 1. 起因

按需验证只在管理员打开分流页、选中规则或保存时才查一次。两个盲区：

- 配置在没人看的时候变了：后台订阅每 10 分钟更新、计量池每小时换池、xray 崩溃后被自动拉起、另一个浏览器里的修改。页面上已有的结果不会自己刷新，规则列表也看不到哪条出了问题。
- 按需验证对核心是抽样问路（每组 ≤2 个样例），真实连接里没被抽到的域名、关键词/正则/geosite 条目是盲区；访问日志能补，但只在打开某条规则时才查。

管理员的诉求是"确保用户走的是对的分流"。本设计让面板**自己**持续地做这两件事，并把结果放到规则列表上。

## 2. 目标 / 非目标 / 反目标

目标

- G1 配置一生效，后台把所有启用规则验证一遍，每条规则保存一份最新结果；规则列表每行显示 ✓ / × / ! / 时钟。
- G2 后台持续扫描新进访问日志，发现"访问了某规则的域名、却没走该规则期望出站"的真实连接就把该规则标为不符，并能看到是哪个用户、哪个域名、走到了哪里、什么时候。
- G3 流量走向图上，走错的用户额外连一条红线到右侧的"实际去向"节点。
- G4 侧栏"分流管理"在有规则不符时显示红点。

非目标

- 不做页面定时轮询（核心的路由决定只在配置变化时改变）。
- 不订阅 xray 的 `SubscribeRoutingStats`（需改核心配置、开销大、与访问日志信息重复）。
- 不做客户端侧验证；不新增数据库表。
- 不按规则顺序重算"某条连接本应命中哪条规则"（那等于在面板里手写一份路由语义，违背前置设计 A3）。

反目标

- A1（沿用）没有当前证据不得显示 ✓。
- A2（沿用）验证本身不改核心状态：`PublishResult=false`、不重启、不写配置。后台审计同样遵守。
- A3（沿用）域名归属只用 xray 自己的匹配器。
- A4 后台审计不得和配置下发抢锁、不得在 `RestartXray` 持有 `lock` 期间调验证；不得让用户手动"重新验证"长时间拿不到结果。
- A5 不能让一次 xray 重启在规则列表上"闪一轮红/灰"：核心刚拉起还没就绪时不落结果。

## 3. 方案 1：配置生效后的后台全量验证

### 3.1 "配置已生效"的信号

在 `web/service/xray.go` 加一个包级 `atomic.Uint64` 代次 `xrayApplyGen`。`RestartXray` 里两处递增：`tryHotApply` 返回 true 之后、`p.Start()` 成功之后。崩溃自愈（`CheckXrayRunningJob`）、订阅更新（`SubscriptionJob`）、计量池（`MeterPoolJob`）、各 controller 的改动都走 `RestartXray`，所以一个点覆盖全部路径。导出只读函数 `XrayApplyGeneration() uint64`。

不在 `RestartXray` 内部直接调验证：它持有包级 `lock`，而 `RuntimeSnapshot` 用 `TryLock`，会在自己的锁上拿到 busy。

### 3.2 审计任务

新增 `web/job/route_audit_job.go`，`@every 30s`（`Server.startTask` 注册，`Run` 首行 `defer common.Recover("RouteAuditJob")`）：

- 代次与上次成功审计时不同 → 全量审计。
- 代次未变但距上次成功审计 ≥ 10 分钟 → 兜底全量审计（防漏、也覆盖访问日志开关等不改代次的变化）。
- 审计前先取 `RuntimeSnapshot`：`Running=false` 或 `Busy` → 本轮跳过、不落结果（A5）。核心刚拉起时 `Start()` 是异步的，首次 TestRoute 可能连不上：若本轮所有规则的核心状态都是 `error` 且错误为连接失败，视为"核心未就绪"，不落结果，下一轮（30s 后）再来。
- `verifyMu` 被用户手动验证占着 → 本轮跳过，下一轮再来（A4）。

### 3.3 `VerifyAll`

`RoutingVerifyService.VerifyAll() (map[int]*RuleVerifyResult, error)`：只对**启用**的规则跑；一次取快照、一次 `GetXrayConfig`、一次 `buildOutbounds`、每个域名组的样例与匹配器只算一次，在规则间复用；共享一个 xray API 连接。逐条规则的判定与 `Verify(id)` 同一份代码（把 `Verify` 拆成"准备共享上下文"与"对一条规则判定"两段，`Verify` 自己也走这两段），保证按需与后台口径不漂移。

整轮预算 60s；单次 RPC 仍 3s。超时未完成的规则不落新结果（保留旧结果并标记 `stale`）。

前置设计 §4.2 的"匹配器每次请求构造、不跨请求缓存"约束的是按需请求；后台审计内一轮之内复用是本设计的明确例外。

### 3.4 结果存储

**只存在内存**：`map[ruleId]*RuleVerifyResult` + 每条结果自带 `checkedAt` 与审计时的代次 `applyGen`。每条规则只保留最新一份，新结果整体覆盖旧结果；规则被删除或停用后下一轮审计时移除。

不落库的理由：面板重启（SIGHUP 或进程重启）必然 `RestartXray(true)`，代次一变 30s 内全量重算，持久化收益很低；而新建带 `rule_id` 外键的表会触发 CLAUDE.md 的 id 复用约束（删规则必须级联删 + 兜底清理）。代价：面板刚重启的 30s 内列表显示"未验证"。

手动验证（`POST /aui/routing/rule/verify/:id`）的结果**也写回**这份缓存（同口径），这样页面与列表看到的是同一份。写回时比较代次与 `checkedAt`，只用更新的覆盖更旧的。

### 3.5 接口

- `POST /aui/routing/rule/audit`：返回 `{ applyGen, rules: { [ruleId]: { verdict, checkedAt, applyGen, stale, mismatchUsers: n, anomalyCount: n } } }`，供规则列表与侧栏红点使用。只读。
- 规则级 verdict 取用户里最坏的一档（不符 > 等待下发 > 无法验证 > 已验证），与流量走向图的汇总口径一致；再并入方案 2 的异常（有异常即不符）。
- `POST /aui/routing/rule/verify/:id` 增加可选参数 `cached=1`：有缓存直接返回缓存（选中规则时先秒开），否则现场验证。

## 4. 方案 2：访问日志持续扫描

### 4.1 存什么

不新增表。**访问日志本身就是 7 天的原始记录**（`AccessLog` 有入站、目标、实际出站、时间），异常明细在需要时按需从它查出来（复用 `GroupByTargetRoute` + `buildLogEvidence`）。扫描任务只在内存里维护每条规则的异常摘要：

```
ruleId → { count, lastAt, byUser: { inboundId → { count, lastAt, routes: { routeHead → count } } } }
```

窗口为最近 24 小时（与图上一致）：摘要按小时分桶累加，超过 24 小时的桶丢弃。面板重启后第一次扫描从 `now-24h` 起全量回填一次。

对管理员说的口径："走错的连接记录会保留 7 天（就是访问日志本身），面板对最近 24 小时做持续汇总。"

### 4.2 扫描任务

新增 `web/job/route_anomaly_job.go`，`@every 1m`：

- 增量读：游标为 `(time, id)`。SQLite 自增 id 会复用，日志被清理到 0 行后新行 id 会回到 1，所以条件用 `time > lastTime OR (time = lastTime AND id > lastId)`，不单用 id。
- 每轮最多读 20000 行，读不完下一轮继续。
- 只看 `Accepted=true` 的行。
- 判定语义沿用 `buildLogEvidence`：对每条启用规则，行的入站在规则覆盖范围内、目标命中规则域名组（xray 匹配器）、`routeHead(Route)` 不符合规则期望出站 → 计为该规则的异常。被更高优先级规则遮蔽的域名会被标成下层规则的异常——这与图里现有日志证据一致，是有意的："这条规则在这个域名上没生效"本身就是要告诉管理员的事。
- 匹配器与期望出站按代次缓存（代次变了重建）。
- 访问日志关闭时整个任务空转，摘要清空，接口返回 `accessLog.enabled=false`。

### 4.3 与方案 1 的关系

规则列表/侧栏的状态 = 方案 1 的核心验证结果 ∪ 方案 2 的异常摘要（有异常即不符）。规则修改后，修改之前的异常仍在 24 小时窗口内：列表上显示不符，但悬停说明与明细里写清"最近一次 10:42"，与前置设计 §4.3 同口径。另提供一个"忽略此前的异常"按钮：把该规则的异常摘要清零（只清内存摘要，不删访问日志），用于管理员确认修复后立刻看到新状态。

## 5. 界面

### 5.1 规则列表

每行在现有"生效中/未生效/已停用"（配置层面）之外，加一个与流量走向图同款的状态图标（✓ / × / ! / 时钟），悬停写明来源："核心验证 14:05 通过" / "近 24h 有 3 次走错（最近 10:42）" / "尚未验证"。两者含义不同：前者说"配置能不能生成"，后者说"实际有没有按配置走"。

规则列表每 60s 拉一次 `/rule/audit`（只读、轻量，不触发验证），页面隐藏（`document.hidden`）时暂停。

### 5.2 侧栏红点

有任何启用规则处于"不符"时，侧栏"分流管理"旁显示红点，悬停写"N 条规则存在走错的流量"。由侧栏所在的各页面复用一个轻量 mixin 拉取 `/rule/audit`（同 60s 节奏）。

### 5.3 流量走向图：实际去向

- 选中规则时先用缓存结果秒开，再按现有逻辑决定是否现场验证。
- 用户 verdict 为不符时，按"实际出站"去重，在右侧"去向"节点下方追加实际去向节点：红色虚线边框、标题"实际：{出站备注}"（直连/封禁/节点名/未知出站），最多 3 个，超出合并为"另有 N 个去向"。
- 红线从走错的用户连到对应的实际去向；配置的去向仍保留原样（并排看得出走偏到哪）。
- 核心处于等待下发时不画实际去向（沿用 Ruling 1）。
- 全局规则只有"所有用户"一行，红线从该行出。
- 实际出站的来源：核心样例的 `actualTag` 与访问日志 `others` 的 `route`，两者取并集。

## 6. 文档

CLAUDE.md 的"流量走向验证"一节同步：代次信号的位置、后台审计不得在 `lock` 内调用、结果只在内存、异常摘要的语义与游标处理；"全程只读"的说法保持成立（本设计不新增写库）。

## 7. 验证方式

- 单测：代次在热应用与重启两条路径都递增；审计任务在代次不变/变化/超 10 分钟/核心未就绪/verifyMu 被占时的行为；`VerifyAll` 与逐条 `Verify` 结果一致；缓存覆盖规则（新代次赢）；扫描游标在 id 复用（清空后 id 回到 1）时不漏行；24h 分桶淘汰；异常判定与 `buildLogEvidence` 一致。
- 端到端（真实 xray，前置条件同现有 e2e）：改规则 → 等一轮审计 → `/rule/audit` 显示新结果。
- 前端：模板守卫测试；浏览器验收规则列表图标、侧栏红点、实际去向节点、忽略按钮。

## 8. 我替管理员做的取舍（审阅时重点看）

1. 核心验证结果只存内存，每条规则一份、覆盖；面板重启后约 30s 内显示"未验证"。
2. 走错记录不另建表：原始记录就是访问日志（保留期默认 7 天），面板只在内存里汇总最近 24 小时。
3. 被更高优先级规则遮蔽的域名，会算作下层规则的走错。
4. 规则列表与侧栏每 60s 拉一次状态（不触发验证），页面隐藏时暂停。
5. 实际去向最多画 3 个。
