# 入站共享检测与地区建议 设计文档

日期：2026-09-05
状态：待评审

## 1. 背景与目标

面板当前防止「一个节点被转卖给多人」的手段只有两个：

- `ConcurrencyLimit`（同时在线的不同来源 IP 数上限，`web/service/concurrency.go`）
- `Regions` 地区限制（省份级白名单，管理员手工填写，`web/service/geo.go`）

前者有效但只约束**同时性**，管理员不知道自己该把额度设成几；后者要求管理员事先知道用户在哪，实际上填不出来。两者之间缺一环：**面板知道每个用户实际在哪些地方用，但从不告诉管理员。**

目标是把这份已有的观测变成两件可用的东西：

1. **共享检测** —— 报出「这个入站有 N 小时里，不同省份的 IP 在同时使用」这一事实
2. **地区建议** —— 算出该用户实际活跃的省份集合，让管理员一键填进地区限制

### 设计的支点：并存，而不是位置

区分「用户出门旅游」和「节点被转卖」的，不是出现了新地区，而是**新旧地区是否同时活跃**：

| | 特征 | 并存小时数 |
|---|---|---|
| 旅游（位置迁移） | 旧地区停止活跃，新地区开始活跃 | 极少，交界处 1–2 小时 |
| 转卖（位置并存） | 两地长期各自活跃 | 持续累积 |

任何按「位置」判定的方案都必然误伤旅游；按「并存时长」判定的方案对旅游天然免疫。整份设计建立在这一条上。

### 非目标

- **不做任何自动处置。** 不自动封禁、不自动限速、不自动写入地区限制。检测只产出事实，处置由管理员决定。理由见 §9。
- 不做阈值配置项。判定参数写死为常量，理由见 §5.1。
- 不做「已知/忽略」标记。先跑一段时间看真实数据分布，再决定要不要。
- 不改动 `ConcurrencyLimit`、地区限制、封禁的任何现有行为。
- 不做多 UUID / 每设备一凭证。本项目架构是**一个入站一个用户**（前端只编辑 `settings.<protocol>es[0]`），那是另一个量级的改动。

### 明确不采用的方案：TOFU 自动地区绑定

原始需求是「新建入站时地区限制留空，用户第一次连上来就把归属地自动写进去」。否决理由，每一条都是这个代码库里的具体事实：

1. **粒度错位。** 地区限制是省份级（`web/html/xui/form/inbound.html:98`，数据源 `ipdb`）。江苏一个省 8000 万人——转卖给同省的人这道锁完全不存在，而用户出个差锁立刻生效。防不住该防的，挡住了不该挡的。
2. **一次采样定终身，而采样不可靠。** 蜂窝出口 IP 经常落在省会甚至跨省的运营商出口；第一次连接可能发生在机场 WiFi。采错了用户无法自救，只会认为节点坏了。
3. **会静默触发拓扑变更。** `database/model/model.go:106`：启用地区限制且未指定监听地址时，入站被强制改为 `0.0.0.0`（纯 IPv4）。后台自动写入意味着该入站悄悄从双栈变成只监听 IPv4，**所有走 IPv6 的客户端突然连不上**，而面板上一切正常。
4. **失败方向与全项目原则相反。** 本仓库反复贯彻「宁可规则不生效让用户察觉，也绝不静默出错」（`web/service/routing_inject.go`）。TOFU 自动写入恰好是静默地把人锁在门外。

需要知道的机制细节：地区限制是**路由层**丢弃（`buildGeoRules` 生成 `ext:a-ui-geo.dat:!TAG` 取反规则），不是入站层拒绝。外地用户的表现是「能连上但没网」，不是「连不上」。

### 2.1 由现状推出的两条硬约束

**约束一：不能把检测建在 `AccessLog` 上。** 访问日志默认关闭，功能装上去默认就是死的；保留期由另一个设置项控制，管理员调短时检测窗口会跟着悄悄缩水，而面板不会有任何表示。正是本仓库最忌讳的静默失效。

**约束二：不能依赖并发判定去驱动采样。** `Enforce()` 的早退意味着「没人设并发额度」时 `sample()` 根本不跑。若把采集挂在它后面，检测在最常见的默认配置下无声失效。因此需要独立的采样任务（§4.1）。

## 3. 数据模型

新增一张小时桶表，与 `model.TrafficBucket` 同构，落在**同一个独立库**（`database.GetTrafficDB()`）——分库理由与用量历史完全相同：高频写入不该和面板的普通操作抢主库那把 SQLite 写锁。

```
InboundIPHour
  InboundId      int     索引，与 TrafficBucket 同样按 id 存（tag 会随端口变化）
  IP             string
  Province       string  空串表示归属地未知（IPv6 / 库未加载 / 库中查无此段）
  HourStart      int64   UTC 整点毫秒
  ActiveSeconds  int
  唯一索引 (InboundId, IP, HourStart)
```

### 3.1 为什么不用更省的 `(ip, first_seen, last_seen)`

一行一个 IP，数据量小十倍，但区分不了「A 早上用、B 下午用」与「A、B 全天同时用」——两者的 `[first_seen, last_seen]` 区间都覆盖一整天。而这个区分正是整个功能的全部价值。省不得。

### 3.2 时区：按 UTC 对齐，与 `TrafficBucket` 刻意相反

`TrafficBucket` 按面板时区对齐，代价是改时区后历史桶与新刻度不相交、图整段消失（CLAUDE.md 记录了实测后果）。

这张表**不跟面板时区**。它唯一的消费者是「同一小时内是否并存」，而该判定只关心两条记录落不落在同一个桶里，桶的绝对位置无关——UTC 与本地时区在此完全等价。既然等价，就不该背上改时区历史失效那个包袱。

代价：半小时时区（`Asia/Kolkata`、`Asia/Tehran`）下，明细页的时段会显示成 `14:30–15:30`。展示时按面板时区格式化标签，判定不受影响。

## 4. 采集

### 4.1 独立采样任务

新增 `SharingSampleJob`，`@every 30s`，独立于 `ConcurrencyJob`（约束二）。每轮：

1. 调 `OnlineService.sample()`。内部的最小间隔去重保证它与并发判定的每秒采样共存而不重复读连接表。
2. 取 tracker 快照。对每个 `(inboundId, ip)`，若 `lastActiveAt` 落在最近 30 秒内，视为这 30 秒活跃。
3. 在内存里给该 `(inboundId, ip, 当前UTC小时)` 累加 30 秒。
4. 累计满 60 秒时落库；此后每再满 60 秒 `UPDATE` 一次 `ActiveSeconds`。
5. 跨小时时把内存累计冲进上一个小时的桶，新小时从零开始。**不满 60 秒的余量直接丢弃，不跨小时结转**——结转会让一个每小时只用 30 秒的扫描器攒够门槛落库，正好绕开 §4.2 第二道门槛。

并存判定的粒度是小时，30 秒采样精度绰绰有余。无条件运行的成本是每 30 秒一次 netlink dump——`ConcurrencyJob` 在有额度时本就每秒做同样的事。

**不加功能开关。** 默认关闭等于装了没用（`accessLogEnable` 就是这个下场）；默认开启则开关无意义。少一个设置项也就少 5 处改动和一处静默失效风险。

### 4.2 写入门槛：入站端口在公网上，会被扫

若每个建立过 TCP 连接的来源 IP 都落一行，一次端口扫描就能在一小时内塞进几千行，保留期压不住，明细页也会被垃圾淹没。三道门槛：

1. **活跃判据是「有字节增长」，不是「有连接」。** 直接复用 `lastActiveAt`（`online.go:90` 已经把它和 `firstSeen` 分开维护）。纯扫描、失败握手不产生字节增长，天然不入库。
2. **单小时累计满 60 秒才落库。** 一次性探测、误连到不了 60 秒；真实使用轻松超过。既压行数，也提高信号质量——并存判定要的本就是「两边都在实质使用」。
3. **单入站单小时最多 50 行**，超出丢弃并记一条 `logger.Warning`。不是为正常场景（正常一小时 2–3 行），是为被针对性刷时表的大小有确定天花板。

### 4.3 归属地解析

落库时用 `ipdbService` 解析 `Province`。解析不到（IPv6、库未加载、库中查无此段）时存空串，**不跳过该行**——IP 维度的并存信息仍然有价值，只是判定会降级（§6.3）。

## 5. 判定

### 5.1 只报事实，不做分级

**不设「疑似」阈值，不做红黄标。** 分级等于面板替管理员下判断，而阈值一旦调不好，告警就变成噪声或漏报。改为直接显示 `并存 37 小时 / 3 省` 这样的事实，由管理员权衡。

唯一的常量是**显示下限：并存小时数 ≥ 3 才打标**。它只用来挡掉旅游迁移交界那 1–2 小时的噪声，不承担判断职责。

### 5.2 并存小时的定义

某个 `HourStart` 下，该入站存在**至少两条 `Province` 不同且都非空**的记录 → 这一小时计为一个**省份并存小时**。

降级定义：某个 `HourStart` 下存在**至少两个不同的 IP** → 这一小时计为一个 **IP 并存小时**。它只在该入站窗口内**所有**记录的 `Province` 都为空时（IPv6 来源、或归属地库未加载）才被使用并展示，见 §6.3。两者不混用——一旦有任何一条记录带上了省份，就以省份口径为准，否则同一个数字会时而是省、时而是 IP，管理员无从判断自己在看什么。

推论（都要有回归测试钉住）：

- 同省多 IP（一个人的手机 + 宽带）→ **不算并存**
- 位置迁移（旧省停止活跃后新省才出现）→ 不产生同一小时的两条记录 → **不算并存**
- 错峰使用（白天甲、晚上乙）→ 落在不同小时 → **不算并存**（已知漏检，见 §9）

### 5.3 判定窗口

固定 7 天。够长能看出持续并存，够短不会让三个月前的一次旅游一直挂着。保留期 30 天（§7），多出来的部分供明细页回溯。

### 5.4 地区建议

建议值 = 窗口内按 `ActiveSeconds` 排序、累计占比达到 95% 的省份集合。正常用户是 `[江苏]`；旅游过的是 `[江苏, 上海]`。

**其中有个必须处理的坑：若该入站正在被共享，建议值会把买家的省份一并算进去——面板等于在帮管理员把转卖合法化。** 而且这一步完全静默：点了「采纳」，界面一切正常，实际上刚给买家发了通行证。

处理：建议照常显示，但**并存记录中出现过的省份单独标出**，由管理员决定剔除哪个。**不自动剔除**——面板分不清「买家的省」和「用户老家常挂的设备」，猜错两个方向都是错的。

## 6. 面板呈现与接口

### 6.1 并进已有的「地区」列，不新增列

不只因为主列表已有 14 列：并存告警本就是地区相关的信息，而采纳建议改的正是这一列的值。看到问题和处理问题在同一个位置。

| 状态 | 「地区」列 |
|---|---|
| 无限制、无并存 | `不限制`（现状不变） |
| 无限制、有并存 | `不限制` + 橙色标 `并存 37h / 3省` |
| 已设限制 | `江苏`（现状不变；有并存时同样追加标记） |

### 6.2 明细走 modal，不塞进展开行

展开行已有两块内容，再加第三块会长到没法用。点橙色标记弹出，三段：

1. **概要** —— 7 天并存 37 小时，涉及江苏、上海、广东
2. **并存时段表** —— 哪一小时、当时同时活跃的省份与 IP。这是管理员判断「转卖还是出差」的原始证据，30 天可回溯
3. **地区建议** —— 建议集合 + 并存省份单独标出 + 「填入地区限制」按钮

按钮的行为是**打开入站编辑框并把地区填好，不直接保存**。管理员确认后走现有保存流程，复用 `EncodeRegionsStrict` 校验与整条配置生成链，不新开写入路径。

编辑框在此时必须提示：**启用地区限制会让该入站变成只监听 IPv4**（`database/model/model.go:106`），走 IPv6 的客户端会立刻连不上。这个副作用在 TOFU 方案里是地雷，在手动确认下只要提示到位就不是问题。

实现约束：新 modal 必须留在 `<a-layout id="app">` 内。Vue 2 只编译 `el` 那棵子树，写在外面按钮点了毫无反应且控制台不报错——分流页踩过，`TestVueDirectivesLiveInsideAVueRoot` 守着。

### 6.3 降级状态必须说人话

`ipdb` 未加载或来源是 IPv6 时拿不到省份。标记退化为 `并存 37h / 3 IP`，tooltip 明说：**IP 归属地库未加载（或来源为 IPv6），当前只能按 IP 判定，同一个人的手机与宽带会被算成两个。** 不能让管理员看着「3 IP 并存」以为抓到了转卖。

### 6.4 接口：新增两个，不动现有的

- `GET /aui/inbound/coexistSummary` → `{inboundId: {hours, provinces}}`，一次 `GROUP BY`
- `GET /aui/inbound/coexistDetail/:id` → 30 天明细

**不往现有入站列表接口塞字段**：不改已有接口契约，且天然 fail open——summary 查询失败时列表照常渲染，只是没有橙色标记。反过来把聚合塞进列表主接口，一次慢查询就能让整个入站列表打不开。

## 7. 保留期与清理

一行约 100 字节（含索引开销），一个入站每小时平均 2 个活跃 IP：7 天约 340 KB / 10 入站，30 天约 1.5 MB / 10 入站。磁盘不是约束，约束是「有没有人看」。

**判定窗口 7 天，保留期 30 天。** 多出来的 23 天让明细页能回溯，判断「一直在共享」还是「上个月出了趟差」。

最坏情况有确定上限：50 行 × 24 小时 × 30 天 × 100 字节 ≈ 3.6 MB / 入站（§4.2 第三道门槛保证）。

### 7.1 三道清理，缺一不可

1. **删除入站时连带删。** 在 `DelInbound` 里加第四处，照访问日志与用量历史的写法：失败只告警不阻断，由兜底清理收尾。不能只靠兜底——兜底每小时才跑一次，这一小时内新建的入站会**继承上一个用户的并存记录**（SQLite 复用自增 id），新客户一进来就被标「并存 200 小时」，而那是别人的数据。
2. **保留期清理。** 删除 `HourStart` 早于 30 天的行，挂进已有的 `TrafficCleanupJob`，不新开任务。
3. **孤儿兜底。** `PruneOrphans` 清掉 `InboundId` 已不存在的残留，防第 1 道漏掉的路径。

保留期为常量而非设置项，与 §4.1 同理：这张表的消费者只有本功能，多一个设置项就多 5 处改动和一处静默失效风险。

## 8. 失败模式与能力边界

三条必须写进界面、不能只写在文档里：

1. **IPv6 拿不到归属地**（`util/ipdb/ipdb.go:64`）。双栈入站上走 IPv6 的用户，省份并存判定对他**完全失效**，只能退化成 IP 数。
2. **运营商出口会漂移。** 手机一小时内从江苏出口切到上海出口是真实存在的误报源。这也是「只告警不处置」正确的又一个理由——自动处置方案在这里会直接封掉正常用户。
3. **同省多 IP 不算并存**（§5.2），所以一个人多设备不会误报。

其他边界：

- **面板重启**：`onlineTracker` 是纯内存的。内存累计每满 60 秒落库一次，重启最多丢当前那一分钟。不为一分钟精度引入持久化恢复逻辑。
- **`netdiag` 不支持的平台**：与并发限制同样失效。照 `ConcurrencyJob` 的做法只提示一次，不每 30 秒刷日志。
- **采集失败**：只 `logger.Warning`，绝不阻断任何既有流程。检测是辅助手段。

## 9. 已知漏检与诚实的能力声明

**错峰共享（白天甲用、晚上乙用）检测不到。** 落在不同小时，不产生并存记录。可以靠「7 天内去重活跃 IP 数 / 省份数」抓到，但正常用户 7 天内十几个 IP、横跨 2–3 个省是常态（家宽换 IP + 蜂窝出口漂移），拿它判定必然大量误报。本期不做。

更根本的一条，需要写进面板文案：**在 vmess / vless 这个协议栈里，「确保只有用户自己用」技术上做不到。** 凭证就是一个 UUID，拿到即可复制。能做的是抬高共享成本、让共享可被发现：并发限制让共享难用，限速让共享不值，本功能让共享无法隐藏。任何声称能「杜绝」的方案（包括 TOFU 地区绑定）实际效果都只是给不懂技术的买家制造麻烦，代价却是正常用户被误伤。

## 10. 测试

按仓库现有模式（`web/service/*_test.go` 纯逻辑，必要时真实依赖）：

**判定算法**（核心，纯函数，四条各一个用例）：
- 转卖场景（两省长期并存）→ 报出对应小时数
- **旅游场景（迁移，不并存）→ 报 0 小时**。整个设计的支点，必须钉住
- 错峰场景（不同小时）→ 报 0 小时
- 同省多 IP → 报 0 小时

**清理三道**：
- 保留期只删过期行，不误删窗口内数据
- `DelInbound` 连带删。专门测——它防的是 SQLite 复用 id 导致新用户继承旧记录，而那个 bug 的表征是「面板显示得完全合理，只是数据是别人的」
- `PruneOrphans` 清掉孤儿

**写入门槛**：不满 60 秒不落库；单入站单小时 50 行上限生效并记警告。

**地区建议**：95% 覆盖集合算对；并存省份被单独标出；**有并存时不自动剔除**。

**归属地降级**：`Province` 为空的行不参与省份并存判定，但计入 IP 数。

**前端**：`TestAllTemplatesParse` 与 `TestVueDirectivesLiveInsideAVueRoot` 自动覆盖新 modal，无需额外用例。
