# 地区限制全自动化（第二期）设计

接 `2026-11-09-auto-region-design.md` 与 `2026-11-09-region-flexibility-auto-travel-design.md`。

## 意图

管理员原话：「所有的判断都是自动化过程，不用我出手的，因为我不常看后台」。第一期里凡是「交给管理员确认」
（pending）的地方，在一个不看后台的管理员面前等于「永远不设限制」；凡是「需要管理员手动改地区」的地方
（长住外地），等于「用户第 10 天起被一直拦着」。这一期把这些判断全部改成系统自动做，并补上场景模拟里
暴露的防共享漏洞，同时修掉 IP 归属地库 / 地区规则的遗留问题。

防共享优先：分不清的时候（错峰共享 ≡ 每天跨省通勤；搬家 ≡ 账号转手），选「只放一个省」的那一侧，
正常的移动交给有防共享门槛的自动出差放行。每一条这样的取舍都以 Ruling 记入台账、写进交付报告。

## 总开关语义（`autoRegionEnable`，默认关 → 升级后行为零变化）

打开后，所有启用的入站由系统管理：

1. **没有地区限制的入站**：观察期满后自动设置为**一个省**（见下）。不再产生「待确认」。
2. **已有地区限制、从未被系统接管过的入站**（没有状态行）：需要认证的入站一次性打开自动出差放行，
   写一行 `adopted` 状态。之后管理员在表单里关掉它，系统不再改回来（有状态行就不再接管）。
   这是让 v1.47.0 时手工设置地区的存量入站也能「全程自动」的唯一途径。
3. **长住外地自动改地区**（见下），只在总开关开着时发生。
4. 打开总开关要求访问日志开着（`entity.CheckValid` 拒绝「总开关开 + 访问日志关」；设置页打开总开关时
   自动打开访问日志）：没有访问日志，自动出差放行发现不了被拦的人，自动设置之后用户出省就被一直拦着。

## 自动设置地区：永远只设一个省

`decideAutoRegion` 只有 wait / apply / unsure 三种结论：

- 观察期、最近在用、稳定天数三道门槛不变。
- 建议（覆盖 95% 活跃时长的省份）只有一个省 → 设置它。
- 建议有多个省：数据跨度不足 3 天 → wait（多看两天，主省份才认得准）；否则设置**主省份**
  （`dominantProvince`：有实质流量的天数最多，平局按活跃时长，再平按省名），其余省份交给自动出差放行。
  不再把多个省一起写进允许集——那会把错峰共享者的省永久合法化（第一期方案 A 留下的缺口）。
- 「设置后会被拦、而且自动出差放行也救不了」的流量（来源没有可放行的省份：境外、IPv6、归属地不明）
  占比超过 `autoRegionMaxBlockedPercent`：有共享迹象（异地同时使用、风险 ≥ 中）照样设置，没有则 wait。
- 访问日志关着 → wait（兜底；正常情况下设置校验已经挡住）。
- 每轮开头删除残留的 pending 行；确认 / 忽略的接口与弹窗删除（不再有 pending）。撤销保留。

## 长住外地：自动改地区（场景一）

在自动出差放行任务里判定，条件全部满足才改：

- 总开关开着、入站开着自动出差放行、入站需要认证、观测数据新鲜；
- 有一张生效中的**单省自动通行证**（省 B）；
- 家里（存储的地区）连续 `autoTravelRelocateDays` 天（新设置项，默认 5，0~7，0 = 不自动改）没有实质使用，此刻也不在用；
- B 在这段时间里至少有 min(3, 天数) 天有实质使用；
- 共享风险读得出、且低于「中」。

一个事务：地区比较后写入（仍是旧值才改）为 `["B"]`，结束通行证（新结束原因 `relocated`），状态行
无条件写成 `applied`，并记下 `PrevRegions`（新列）。「需要留意」里 7 天内显示，撤销 = 恢复旧地区并关闭
这个入站的自动出差放行（管理员撤销即表示这个入站不要自动化）。过期页面防护扩展为：7 天内拒绝把地区写回
`PrevRegions`。`autoTravelRelocateDays > autoTravelMonthlyDays` 时通行证撑不到判定那天，设置校验拒绝。

## 自动出差放行：补防共享门槛（场景二）

全部在纯函数 `decideAutoTravel` 里，冷却窗口沿用 `autoTravelCooldownDays`（为 0 时这几条一起关闭）：

- **本人在用时外地被拦过**：冷却窗口内，某省的来源在家里有实质使用的同一小时或前一小时被拦过（与
  「需要留意」标「疑似共享」同一判据）→ 不对这个省自动放行。只在即将发放时查访问日志（按 IP×小时聚合）。
- **短命通行证**：冷却窗口内，同一省有 ≥2 张自动通行证在发出后不到 24 小时就因「家里恢复使用」收回 →
  不对这个省自动放行；30 天内 ≥3 张 → 停 30 天。
- **反复同时使用**：30 天内第二次因「家里与外地同时在用」收回 → 整个入站暂停 30 天（自动到期，
  不需要管理员重新打开）。
- **无认证的入站**（socks noauth、http 没有账号、dokodemo-door、shadowsocks 的 none/plain）不自动放行、
  不自动改地区：扫描器的连接在访问日志里也是「已接受」。自动设置地区时也不替它们打开自动出差放行。
- **观测数据不新鲜**（`SharingService.Sample` 最近一次成功超过 3 分钟；库没打开不算成功）→ 不发放、
  不续期、不改地区：采样断了，家里看起来就是「一直没在用」，收回也触发不了。
- 「候选省份已在存储的地区里」由 `recentGeoBlocked` 的匹配器过滤保证，用测试钉住。

## IP 归属地库与地区规则

按依赖顺序：

1. **多省缺一个察觉不到**：生成时逐省对照 IP 库的省份列表。缺省份 → 有上一次的允许集就沿用（stale），
   没有就用剩下省份的段并标新模式 `partial`（「需要留意」可显示）。
2. **降级状态如实**：生成算出 `{降级状态, 每个入站的 dat 代码}`，只有核心真的用上这份配置
   （热应用成功、进程启动成功、或配置与核心一致的空操作分支）才提交为「已生效」。`GeoDegradedInbounds()`
   返回已生效的。生成结果与已生效的不同 → 置重启标志，原因消失后会自动重新下发。
3. **证据匹配器认得锁死的入站**：已生效状态里锁死的入站，所有来源都算被地区规则拦下；匹配器用已生效的代码。
4. **IP 库更新后核心用上新网段**：dat 代码按内容寻址——`regionTag`（省份集合）仍是 last-known-good 的键，
   dat 里的代码 = tag + 内容哈希。xray 的 IP 集合缓存按「文件:代码」做键，内容变代码就变，热应用不会再命中
   旧集合。ruleTag 不再带 dat 哈希。写 dat 时保留正在运行的配置引用的代码，任何一次生成都不会让另一份
   配置（进程重启、校验）找不到代码。
5. **入站 id 复用继承旧用量**：新建入站拿到 id 后，清掉其它库里这个 id 的残留行（用量小时行、风险快照、
   用量历史、访问日志、域名统计、计量池）。

## 不做的事

- 不改「家里静默」默认值（2 小时）；报告里给出调到 8 小时的模拟数据，由管理员决定。
- 不做通知渠道（本项目没有 Telegram 等推送）。
- 最后的自查范围是本期与第一期的全部未提交改动，不是全仓库。
