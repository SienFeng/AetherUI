# IP 目标与分流流量的计量覆盖 设计文档

状态：草案，待评审
日期：2026-09-09
前置：[2026-09-06 域名维度流量归因与 Top 榜单](2026-09-06-domain-traffic-attribution-design.md)（第一、二期）

本文是计量子系统的**第三期**。前两期建立了「访问次数榜」与「按域名的真实字节数」，
本期解决它们在真实生产数据上暴露出的两个覆盖缺口。

---

## 1. 背景：一台生产机上的 0.014%

2026-09-09，管理员发现一个入站上传了大量流量，但 Top 域名榜单上查不到它去了哪。
在那台机器（香港，16 个启用入站，单核 972 MB）上取到的实测数据：

```
入站 7「微信：ljdzjj」最近 24 小时
  入站计数器      上传 2.53 GB   下载 0.16 GB      ← 上传是下载的 16 倍
  已归因到域名    上传 0.37 MB   下载 2.35 MB
  上传归因率      0.014%
```

榜单上排第一的域名（按上传）是 `acspubs.org`，215 KB。而那 2.53 GB 在
访问日志里指向一个**没有域名的目标**：

```
72.235.209.83:54250    2171 次连接    走 a-ui-default（直连）
```

Hawaiian Telcom（夏威夷家庭宽带）的一个 IP，高位端口，24 小时不间断（凌晨 3 点
仍有 69 次/小时），来自 5 个不同的源 IP。

### 1.1 三条缺口，按流量占比排序

| 缺口 | 这台机器上的表现 | 根因 |
|---|---|---|
| **纯 IP 目标无法计量** | 2171 次直连、约 2.4 GB | `IsRegistrable` 对 IPv4/IPv6 字面量返回 false，不得进池；计量规则是 `domain:` 条件，对 IP 目标结构上不可能命中 |
| **被分流带走的流量无法计量** | `chatgpt.com` 2924 次，字节恒 0 | 计量规则排在所有规则最后，管理员的分流规则（ChatGPT → IProyal）先命中，计量出站永远收不到字节 |
| **被 block 的流量无法计量** | 3050 次 | 客户端已把数据传到面板（入站计数器记了），出站直接丢弃（出站计数器为 0）。**结构性缺口，本期不解决** |

第二条还有一个**正在持续发生的副作用**：池表里
`chatgpt.com` 与 `openai.com` 的 `probe_zero_rounds` 都已经到 2，
再一轮（`meterProbeGiveUpRounds = 3`）就会被当成「只有连接数、没有流量的域名」
踢出池并冷却 24 小时，然后因访问次数高重新进来，再白占 3 轮 —— 一个永不停止的空转循环。

## 2. 已核实的事实

本节的每一条都有实测支撑。它们推翻了立项时的两个先验判断，是本期方案选型的全部依据。

### 2.1 池容量不是瓶颈（推翻的判断之一）

立项时的直觉是「池太小（每人 12 个槽位），扩容就能提高覆盖率」。实测否定了它。

入站 7 的池里 10 个活跃成员是：

```
acspubs.org  adobe.com  apple.com  google.com  icloud.com
microsoft.com  oaistatic.com  openai.com  chatgpt.com  vscode-sync.trafficmanager.net
```

全是小流量域名，24 小时合计 2.75 MB。而那 2.53 GB 集中在**一个**目标上，
它进池只需要 **1 个槽位** —— 但它没有资格参选。

**结论：池不是不够大，是装错了东西。** 把池从 12 扩到 600，装进来的是第 13
到第 600 个小流量域名，覆盖率从 0.014% 涨到 0.02%。扩池不是本期方案。

### 2.2 计量出站的边际代价（推翻的判断之二）

立项时怀疑「配置解析慢是因为域名组里那 2.4 MB 的订阅列表」。实测否定了它。

本地对照实验（darwin/arm64，xray 26.7.28，`run -test`，各档取 3 次最小值）：

| 组合 | 基线（0 个计量出站） | 每个计量出站 |
|---|---|---|
| 12 万条域名列表 + ip 守卫 | 0.40 秒 | **14.84 ms** |
| `geosite:cn` + ip 守卫 | 0.12 秒 | 8.19 ms |
| `geosite:cn`，无 ip 守卫 | 0.17 秒 | 4.65 ms |

两条结论：

1. **基线可以忽略。** 3381.9 KB 的配置 0.40 秒，401.9 KB 的配置 12.41 秒 ——
   耗时与配置体积甚至是反相关的。时间花在把规则**编译成匹配器**上，不在读取。
   这一点必须写下来，因为「配置太大」是个太自然而错误的直觉。
2. **大域名列表让每个计量出站的代价接近翻倍**（14.84 vs 8.19 ms）。所以把管理员
   的「中国域名列表」域名组换成 `geosite:cn` 能让本期的全部代价减半，
   而这**不需要任何代码改动**。

生产机（单核）上的实测斜率是 **130 ms/个**，约为本地的 8.8 倍。

### 2.3 xray 整进程重启的真实频率

这是决定「代价可不可接受」的关键数据，而且极易误读。19 小时的面板日志里有
3 次 `get xray traffic failed: connection refused`，但其中 2 次是**面板自身重启**
（进程 PID 从 52806 → 58493 → 64252 变化可证），只有 1 次是 xray 整进程重启：

```
09-09 16:30   面板重启（PID 变化）
09-10 04:05   xray 整进程重启   ← 域名组订阅更新触发，每天一次
09-10 10:07   面板重启（管理员更新到 v1.24.1）
```

同期每小时 30 分都有一条 `xray 配置改动已通过控制面下发，无需重启` ——
**计量池每小时重算，19 小时 19 次全部走热应用，零重启**。

**所以本期新增的配置解析代价，只在每天凌晨 4:05 那一次付。** 平时的池变动
走 gRPC 热增删，不受影响。

> **附带发现（本期不处理）**：`tryHotApply` 的全部失败路径都是 `logger.Debug`
> （`web/service/xray.go:173-223`），只有成功那条是 `Info`。默认日志级别下，
> 「热应用失败退回重启」是完全静默的 —— 04:05 那次究竟是判定不能热应用，
> 还是下发失败退回，现在查不出来。这是可观测性缺口，值得单独修。

### 2.4 xray 不提供按域名的流量（沿用第二期结论）

`app/stats/command` 的计数器只有 `inbound>>>tag`、`outbound>>>tag`、`user>>>email`
三个维度，没有域名维度；访问日志（`common/log/access.go` 的 `AccessMessage`）
没有任何长度字段，而且在连接**建立**时就写出。

因此「让每个要计量的对象拥有自己的出站 tag」是唯一可行路径。本期不改变这个前提。

## 3. 目标与非目标

### 目标

1. **纯 IP 目标可被计量**（改动 A）。做完之后，上述 2.4 GB 落到 `72.235.209.83` 自己那一行。
2. **被分流规则带走的流量可被计量**（改动 B），粒度是「入站 × 分流规则」。
3. 二者都不改变分流结果；B 因为原理上做不到「完全不改变」，用总开关兜底（§5.5）。
4. 覆盖率从 0.014% 提到 **85~95%**（估算依据见 §8.2）。

> **口径提醒**：面板的 `up`/`down` 是**用户视角**——`up` 是客户端发给服务器
> （用户上传），`down` 是服务器发给客户端（用户下载），对应 xray 的
> `inbound>>>tag>>>traffic>>>uplink/downlink`（`xray/process.go:286`）。
> 出站计数器的方向是服务器视角（`uplink` = 服务器发给目标）。两者方向相反，
> 实施时任何一处写反都不会报错，只会让榜单的上传/下载两列对调，
> 而「上传远大于下载」正是本期这个案例的核心异常信号。

### 非目标

- **不追求 100% 对账。** 三个结构性缺口无法消除：被 block 的流量（出站字节恒为 0）、
  入站计的加密流与出站计的明文流之间 3~8% 的协议开销差、以及仍在池外的长尾域名。
  UI 必须继续如实标注为「约」。
- **不扩池。** 理由见 §2.1。池容量策略（`meterOutboundBudget = 200`、
  `meterPoolCapMax = 60`）本期一个字节都不改。
- **不做「按需盯人」的单入站全量计量开关。** 那是另一个功能，与本期正交。
- **不改访问日志、不改 `DomainStat` 的采集链路**（`RecordMetered` 挂在
  `AddTraffic` 上这条不变）。

## 4. 改动 A：把纯 IP 目标纳入计量

### 4.1 准入：`IsRegistrable` 之外增加一条 IP 通道

现在有三处调用 `domain.IsRegistrable` 做准入，各自的处理要分开对待：

| 位置 | 现在的作用 | 改动 |
|---|---|---|
| `meter_pool.go:166`（`buildMeterCandidates`） | 候选过滤，IP 被丢弃 | 放行 IP 字面量 |
| `routing_inject.go:198`（`filterMeterPool`） | 生成期二次过滤 | 放行 IP 字面量 |
| `domain_stat.go:186`（`Registrable`） | 归并访问目标 | **不动**，它本来就原样返回 IP |

新增判定函数放在 `util/domain`，与 `IsRegistrable` 并列：

```go
// IsMeterable 判断一个归并后的目标能否进计量池：注册域名，或 IP 字面量。
// 公共后缀本身（"com"）、无点主机名（"localhost"）仍然拒绝——前者会生成
// domain:com 这种命中全部 .com 的规则，把入站几乎全部流量吸进一个计量出站。
func IsMeterable(d string) bool
```

**不把 IP 直接塞进 `IsRegistrable`**：那个函数的语义是「是不是注册域名」，
被池以外的地方使用；改它的语义会在看不见的地方产生副作用。

### 4.2 规则形态：IP 目标用 `ip` 条件，且**不带** ip 守卫

域名计量规则（现状，`buildMeterRules`）：

```json
{"type":"field","inboundTag":["inbound-2210"],
 "domain":["domain:google.com"],
 "ip":["0.0.0.0/0","::/0"],          // ← ip 守卫，仅 domainStrategy 解析时才加
 "outboundTag":"a-ui-meter-7-google.com"}
```

IP 计量规则（新增）：

```json
{"type":"field","inboundTag":["inbound-2210"],
 "ip":["72.235.209.83/32"],
 "outboundTag":"a-ui-meter-7-72.235.209.83"}
```

**为什么不需要 ip 守卫**：守卫的作用是让计量规则在「第一遍匹配」中必然不命中
（域名目标此时还没有 IP），从而不屏蔽掉模板里 `geoip:private → blocked` 这类
只能在第二遍命中的 CIDR 规则（第二期 §6.1）。而 IP 计量规则**本身就是 IP 条件**，
它在第一遍对 IP 字面量目标直接命中——这正是要的行为，加守卫反而是同义反复。

裸 IP 要补掩码（`/32`、`/128`）：`infra/conf` 接受不带掩码的写法，但显式补齐
可以让生成结果逐字节确定，也便于日志与测试比对。

### 4.3 必须承认的语义模糊：IP 行会吸进「解析到该 IP 的域名流量」

计量规则排在所有规则最后。对一个**池外域名**的连接：

- 第一遍：所有域名条件都不命中，IP 条件因目标还是域名也不命中
- 第二遍（仅当 `ipRuleResolveDomain=1`）：解析出 IP，若恰好等于某个池内 IP，命中该 IP 的计量规则

于是 `72.235.209.83` 这一行的字节，可能包含「某个池外域名解析到这个 IP」的流量。

**不打算消除它。** xray 没有任何条件能区分「目标本来就是 IP 字面量」与
「域名解析出来的 IP」。而且从归因的角度这不算错——流量确实发往那个 IP。
实际影响也小：池按流量权重选，大流量域名本来就会进池、在第一遍先被归走。

**但顺序必须固定**：域名计量规则全部排在 IP 计量规则之前。这样域名目标优先
归到域名行，只有归不到域名的才落到 IP 行。

### 4.4 tag 形态与 `ParseMeterTag`

沿用 `model.MeterTag(inboundId, target)`，target 位置放 IP 字符串：

```
a-ui-meter-7-72.235.209.83
a-ui-meter-7-2001:db8::1        ← IPv6
```

`ParseMeterTag` 按**第一个**短横线切分（`meter.go:38`），IPv4 里没有短横线、
IPv6 用冒号，所以两者都能正确反查，**这个函数不用改**。

`IsMeterTag` 判前缀，同样不用改。因此 `model.IsReservedTag` 在分配端 / 生成端 /
导入端 / 校验端的四道 fail-close 防线自动继承，无需任何改动。

> **已验证（2026-09-09）**：IPv6 的 tag 含冒号（`a-ui-meter-7-2001:db8::1`），
> Xray 26.7.28 对含 IPv4/IPv6 两种计量 tag 的完整生成配置返回 `Configuration OK`。
> 回归测试 `TestIPMeterRulesAreAcceptedByRealXray`（`meter_rule_e2e_test.go`）
> 钉住了它，核心升级换掉解析器时会变红。
>
> 万一将来不再被接受，退路是对 IPv6 做一次确定性转写，**绝不能**换成短横线
> ——`ParseMeterTag` 按第一个短横线切分，那会让反查静默错位。

### 4.5 池排序、换池、死计数器：全部不变

`meterAvgBytesPerConn` 的加权排序、`meterMinHoldRounds`、`meterProbeGiveUpRounds`、
`meterCooldown`、`meterSwapMargin`、`meterStaleCounterLimit` 一个都不动。
IP 目标作为普通候选参与同一套竞争。

### 4.6 改动 A 的代价

**出站数量不变。** IP 目标顶替掉本来会被选中的小流量域名，池容量不变，
配置解析耗时不变，凌晨那次重启**一秒都不多**。

## 5. 改动 B：分流流量按「入站 × 分流规则」计量

### 5.1 为什么必须改分流规则本身

计量的原理是「让目标流量走一个带独立 tag 的出站」。被分流的流量已经被管理员的
规则指定了出站（`iproyal`），要给它单独计数，只有一条路：**把那条分流规则的
`outboundTag` 改成一个计量出站，再由计量出站转发到真实出站**。

没有替代方案。往前插规则会改变分流结果；往后追加规则永远轮不到。

### 5.2 粒度：按规则，不按出站

这台机器上有 5 条规则都指向同一个出站：

```
规则 8  Claude   → 常规新加坡分流
规则 9  ChatGPT  → 常规新加坡分流
规则 4  Gemini   → 常规新加坡分流
规则 5  Cursor   → 常规新加坡分流
规则 7  中国域名 → 常规新加坡分流
```

按「入站 × 出站」分账会把这 5 条合并成一个数字，管理员看到的是「走新加坡 800 MB」，
无法回答「他 ChatGPT 用了多少」。所以粒度必须是 **入站 × 规则**。

### 5.3 规则拆分

一条覆盖 N 个入站的分流规则，拆成 N 条，各自指向自己的计量出站：

```json
// 改动前（一条）
{"inboundTag":["inbound-2210","inbound-2180"],"domain":[...],"outboundTag":"a-ui-常规新加坡分流"}

// 改动后（两条）
{"inboundTag":["inbound-2210"],"domain":[...],"outboundTag":"a-ui-meter-r-7-9"}
{"inboundTag":["inbound-2180"],"domain":[...],"outboundTag":"a-ui-meter-r-4-9"}
```

`InboundIds` 为空数组（全局规则）时按**当前全部启用入站**展开——空数组的语义是
「对所有入站生效」，展开后逐字节确定（入站按 id 升序）。

**block 动作的规则不拆**：黑洞出站的字节恒为 0，拆了也只有连接数，
徒增规则数量。它们继续原样进 `blockRules`。

**顺序必须逐字节确定**（注入器第四条不变量）：规则之间仍按 `priority asc, id asc`，
同一条规则展开出来的 N 条按**入站 id 升序**。否则 `Config.Equals` 恒为 false，
那个 10 秒的消费任务会不停重启 xray。

实施时把规则组装抽成 `emitRules`，展开时对每个入站各调一次；形态与抽出前逐字节相同
（`TestInjectProxiedMeterOffIsByteIdentical` 钉住）。

### 5.4 计量出站的构造：克隆，不用链式

两条路都验证过：

| 方案 | 做法 | 取舍 |
|---|---|---|
| 链式 | `{"protocol":"freedom","tag":"...","proxySettings":{"tag":"<真实出站>"}}` | 配置不复制、不会漂移；但每条连接多一层 pipe（`handler.go:272-300` 会 `go handler.Dispatch` 起一对 pipe），单核机器上的开销未实测 |
| **克隆（选用）** | 深拷贝真实出站的完整配置，只换 `tag` | 转发路径与原出站完全一致，无额外开销；配置体积增大（vmess 出站约 300~500 B/个） |

选克隆的决定性理由：**它与现有实现完全同构**。`appendMeterOutbounds`
（`routing_inject.go:229`）现在就是「给池里每个 (入站,域名) 追加一个**默认出站的深拷贝**」，
本期只是把「深拷贝默认出站」换成「深拷贝规则指定的那个出站」，
代码形状、失败模式、测试方式全都不变。链式引入的是一条全新的、未实测的转发路径。

配置不会漂移：生成期每次从 `outbound_nodes` 重新读取并重新深拷贝，
管理员编辑真实出站后，下一个生成周期自动跟随。

**`direct` 动作**（走默认出站）克隆的是 `tagDefaultOutbound` 返回的那个出站，
与 `buildRule` 现在的处理保持一致，绝不硬编码 `model.DefaultOutboundTag`。

### 5.5 被打破的不变量，与总开关

第二期文档里这条是计量子系统的设计前提：

> 计量规则永远排在所有规则的最后……只计量本来会走默认出站的流量。

它的价值在于**风险隔离**：计量子系统出任何错，最坏后果是统计不准，用户流量照走。

改动 B 打破它。计量出站从此承载真实的分流流量：

```
改动前：计量出错 → 榜单数字不对，ChatGPT 照常能用
改动后：计量出错 → 用户的 ChatGPT 直接断
```

而且这类错误在 `run -test` 里可能是合法的（tag 存在、语法正确），
只在运行时表现为连不上——`Process.Start()` 从不回传启动失败，
`/server/status` 会继续显示 `running`。

**缓解：总开关 `meterProxiedTraffic`，默认 0（关）。**

- 关：`buildRules` 的行为与现在逐字节相同，规则不拆、不生成 B 类计量出站。
  **升级后行为零变化**，与 `ipRuleResolveDomain` / `dnsServers` 同一套约定。
- 开：启用 §5.3 / §5.4。出问题在面板上关掉，下一个生成周期恢复（走热应用，不重启）。

按项目约定，新增设置项要动 **5 处**，缺一处的后果见 CLAUDE.md「设置系统」一节
（漏掉 `models.js` 会让整个保存配置接口失败）：

1. `web/service/setting.go` 的 `defaultValueMap` 加 `"meterProxiedTraffic": 0`
2. `web/entity/entity.go` 的 `AllSetting` 加 `MeterProxiedTraffic int`
3. `entity.CheckValid` 加取值校验（仅 0/1）
4. `SettingService` 加 `GetMeterProxiedTraffic()`
5. `web/assets/js/model/models.js` 的 `AllSetting` 构造函数加同名字段

它会进入 xray 配置，所以还要接进 `ValidateSettings`（`routing_validate.go`），
与 `dnsServers` / `ipRuleResolveDomain` 同一条路径：候选值由 `apply` 回调贴到
完整配置上，不能指望 `GetXrayConfig()`（它读的是库里的旧值）。

### 5.6 tag 形态与规则 id 复用

```
a-ui-meter-r-<inboundId>-<ruleId>      例：a-ui-meter-r-7-9
```

`r-` 这一段把 B 类与 A 类（`a-ui-meter-<inboundId>-<target>`）区分开。
`ParseMeterTag` 需要扩展以识别这个形态——**这是本期唯一需要改动的 tag 解析逻辑**，
**实施后确认 `RecordMetered` 不需要改**：`ParseMeterTag` 对 B 类 tag 返回的第二个值
就是 `rule:<id>`，采集链路把它当键原样写库，A 类 B 类自动分流。

**SQLite 会复用被删除的自增 id**（CLAUDE.md「已知偏差」）。规则被删除后新建的规则
可能拿到同一个 id，让残留的计量数据绑到一条毫不相干的规则上——而引用不再悬空，
生成期的跳过防线拦不住。因此：

> **`RoutingRuleService.Del` 必须连带删除该规则的计量数据**，与
> `InboundService.DelInbound` 连带删 `TrafficHistoryService.DeleteByInbound`
> 同构。另需在 `TrafficCleanupJob` 里加一条 `PruneOrphans` 式的兜底。

这是本期新增的第 4 条「存 id 外键 + 被引用方可删除」的组合，
必须照着现有三条 `Check*Refs` 的先例办理。

### 5.7 A 类与 B 类的交互：被分流覆盖的域名会白占池槽位

开了总开关之后，一个被分流规则覆盖的域名（如 `chatgpt.com`）由 B 类计量。
但它同时仍是 A 类池的合法候选——池的排序只看访问次数与已实测字节，
不知道它已经被 B 类接管了。于是它会进池、拿到一个 A 类计量出站和一条排在最后的
规则，而那条规则**永远不会命中**（管理员的分流规则在前先命中），
实测字节恒为 0，3 轮后被 `meterProbeGiveUpRounds` 判为「只有连接数、没有流量」
踢出并冷却 24 小时，24 小时后再回来，如此循环。

**这个循环现在就在发生**（§1.1：`chatgpt.com` 与 `openai.com` 的
`probe_zero_rounds` 已经到 2）。改动 B 不会加剧它，也不会消除它。

**本期接受这个浪费，不做「候选时剔除已被规则覆盖的域名」。** 理由：判断一个域名
是否被某条分流规则覆盖，要把它拿去和域名组的内容做匹配，而单个组可达十几万条
（这台机器的「中国域名列表」有 2.4 MB）；每小时对每个候选做一次这种匹配，
代价远大于浪费掉的槽位。而且 probe 机制本身就是为这种情况设计的自我修正，
浪费被限制在「3 小时槽位 + 24 小时冷却」的循环里。

**但要注意它对 §8.2 覆盖率估算的影响**：这些域名在 A 类里恒为 0，
它们的字节全部来自 B 类。UI 上如果同时显示两行（一行域名 0 字节、
一行规则有字节），会让人以为该域名没有流量。**UI 必须在开关打开时
隐藏 A 类里字节恒为 0 且被 B 类覆盖的行**——或者更简单：
榜单默认按字节排序时，0 字节的行本来就沉底，不做特殊处理。

### 5.8 不需要改 `Config.Equals`

本期新增的内容全部落在 `OutboundConfigs` 与 `RouterConfig` 两个
`json_util.RawMessage` 字段里，它们按字节比较，内容变化天然被察觉
（CLAUDE.md「xray 进程与配置合成」）。新增的设置项 `meterProxiedTraffic`
只影响生成过程、不进 `xray.Config` 结构，同样不需要扩展 `Equals`。

代价是**生成必须逐字节确定**，见 §5.3 的顺序约定。

## 6. 数据模型

> **本节作废（2026-09-10 实施改动 B 后确认）**：A、B 两期都不需要 `Kind` 列。
> A 类的 IP 字面量与 B 类的 `rule:<规则id>` 都直接作为 `DomainStat.Domain` 的键，
> 类型由键的形态推导（`topDomainKind`：先判 `rule:` 前缀，再判 IP，否则域名）；
> `rule:` 不可能与真实目标撞车——`Domain` 列的值全部来自 `domain.Registrable()`，
> 输出永远是注册域名或 IP。`MeterDomain` 池表不参与 B 类计量。下文描述的 GORM
> `AutoMigrate` 不修改已存在索引那个风险因此不复存在。


### 6.1 `model.DomainStat` 新增 `Kind` 列

```go
type DomainStatKind int

const (
    StatKindDomain DomainStatKind = 0 // 注册域名（默认值，老数据自动正确）
    StatKindIP     DomainStatKind = 1 // IP 字面量
    StatKindRule   DomainStatKind = 2 // 分流规则（B 类）
)
```

`Domain` 列的取值随 `Kind` 变化：`StatKindDomain` 存注册域名、`StatKindIP` 存 IP
字符串、`StatKindRule` 存**规则备注 + 规则 id**（备注可为空、可重复，单独用它
无法定位；带上 id 才能在 UI 上点回那条规则）。

**为什么加列而不是给 `Domain` 加前缀**：前缀方案会让 `MergeDomains`、
`TopDomains` 的排序、以及所有既有查询都要先剥前缀，而且一个恰好叫
`ip:1.2.3.4` 的域名（合法的 keyword 写法）会撞车。加列是一次 `AutoMigrate`
就能完成的、语义清晰的改动，默认值 0 让全部历史数据自动落在 `StatKindDomain`。

唯一索引从 `(granularity, inbound_id, domain, bucket_start)` 扩展为
包含 `kind`——否则一个 IP 与一个同名域名（理论上不会撞，但索引必须严谨）会合并成一行。

> **迁移风险，实施前必须先验证**：GORM 的 `AutoMigrate` **不会修改已存在的索引**，
> 它只创建缺失的。直接改结构体上的索引定义，在已有部署上是**静默无效**的——
> 新列加上了，索引还是旧的，而且没有任何一层会报错。可行的做法是给新索引
> 换一个名字让 `AutoMigrate` 去建，旧索引留着不删（多一个索引只有写入开销，
> 不影响正确性）。这条必须在实施时用一个真实的旧库验证，不能只看代码。

### 6.2 `model.MeterDomain` 新增 `Kind` 列

同上，池表也要区分三类成员，否则 `Pool()` 读出来之后无法决定生成哪种规则形态。

## 7. UI 呈现

访问日志弹窗的「Top 域名」页签，列表增加一列**类型**：

```
#  类型    目标                        访问次数    上传      下载
1  IP      72.235.209.83               2495       2.41 GB   118 MB
2  规则    ChatGPT → IProyal (#9)       —          88 MB     412 MB
3  域名    acspubs.org                 131        215 KB    544 KB
```

「规则」行没有访问次数（`—`）：访问次数来自访问日志按域名归并，
与规则不是同一个维度，填 0 会被理解成「没访问过」。

### 7.1 差额分解：让账「平」而不是让差额消失

覆盖率永远到不了 100%（§11），但**每一块差额都应该有名字**。现在的
「本周期该用户约 0% 的流量已归因」除了让人以为系统坏了之外没有任何信息量。

榜单下方给出一份分解：

```
微信：ljdzjj   最近 24 小时   总用量 2.69 GB

  72.235.209.83                  2.38 GB     ← 精确（出站计数器）
  ChatGPT 组 → IProyal            88 MB      ← 精确
  Claude 组 → 新加坡              42 MB      ← 精确
  acspubs.org                    760 KB      ← 精确
  ...
  ──────────────────────────────────────
  已归因合计                     2.42 GB  (90%)
  被封禁丢弃                     3050 次连接，字节数不可得（见 §11.1）
  协议封装开销                   约 190 MB   估算（总量的 3~8%）
  未归因（池外长尾）              78 MB      = 总量 − 已归因 − 估算开销
```

三条约束：

- **精确值与估算值必须在视觉上分开。** 前四行是 xray 计数器直接读出来的，
  「协议封装开销」是按比例估的。混在一起显示会让整份数据的可信度一起塌掉。
- **「未归因」用减法得出，不单独测量。** 它天然吸收所有估算误差，
  这是它作为最后一行的意义；把它做成"精确值"反而是假的。
- **协议开销的比例区间（3~8%）要可配置或至少写在说明里**，不同协议
  （vmess+ws+tls vs vless+vision+reality）的封装开销差别不小，
  写死一个数在别的部署上会失真。

覆盖率那一行的文案要相应调整，把「被你自己的分流规则带走的部分不在其中」
这句删掉——开了总开关之后它不再成立。关着开关时保持原文案。

## 8. 代价评估

### 8.1 配置规模

以那台机器为准（16 启用入站、7 条分流规则、当前 69 个出站 / 104 条规则）：

| 项 | 增量 |
|---|---|
| 改动 A | **0**（IP 顶替域名占用同一批槽位） |
| 改动 B 的计量出站 | 约 +82（6 条非 block 规则按入站展开） |
| 改动 B 的规则 | 约 +76（原 6 条 → 82 条） |

按生产机实测的 130 ms/个：**凌晨那次重启 +15~20 秒**（15 秒 → 30~35 秒）。

把「中国域名列表」换成 `geosite:cn`（零代码）后斜率减半，净增回落到 +8~10 秒，
且基线本身也从 15 秒降到 8 秒左右——**两项合计后，凌晨重启时长与现状基本持平**。

### 8.2 覆盖率估算

入站 7 的 24 小时连接分布：

```
a-ui-block                    3050 次   ← 结构性缺口，永远拿不到字节
a-ui-default                  2188 次   ← 其中 2171 次是 72.235.209.83，改动 A 覆盖
a-ui-服务器ai入栈流量-iproyal   1438 次   ← 改动 B 覆盖
a-ui-常规新加坡分流            1178 次   ← 改动 B 覆盖
a-ui-meter-*                   157 次   ← 已覆盖
```

上传 2.53 GB 里的绝大部分在 `72.235.209.83`（唯一的大流量目标）。
改动 A 单独就能把上传归因率从 0.014% 拉到 **90% 以上**；
改动 B 补上 ChatGPT/Claude 这些下载侧的大头。

剩余缺口：block 那 3050 次的字节（连接建立即被切断，字节量应该很小但非零）、
3~8% 的协议开销差、以及仍在池外的长尾。**保守估计 85~95%。**

## 9. 回退契约

回退到不认识本期改动的旧二进制时：

- **改动 A**：`filterMeterPool` 的 `IsRegistrable` 会把 IP 池行判为「不再是注册域名」
  并剔除，规则与出站都不生成。池表里的 IP 行成为惰性数据，下一轮 `Recompute`
  被正常淘汰。`DomainStat` 里 `kind=1` 的历史行仍会被旧版 `TopDomains` 查出来
  （它不带 `kind` 条件），显示成一个「域名」——**看起来像 IP 的域名行**，
  数字是对的，只是类型标签不见了。可接受。
- **改动 B**：`kind=2` 的行同样会被旧版查出来，`Domain` 列里是规则备注，
  会在榜单上显示成一个奇怪的「域名」。**这是回退后唯一的观感异常**，
  不影响任何判定逻辑。若要干净回退，关掉总开关再降级即可。
- **数据库**：`AutoMigrate` 只加列不删列，回退后新列被忽略。

## 10. 测试策略

沿用第二期的分层：纯函数单测 + 注入器结构测试 + 真实 xray 的 e2e。

必须有的用例：

1. `IsMeterable`：IPv4/IPv6 字面量放行，公共后缀本身、无点主机名、带末尾点仍拒绝。
2. IP 计量规则**不带** ip 守卫，且掩码被补齐；域名计量规则的守卫行为不变。
3. **顺序**：域名计量规则全部排在 IP 计量规则之前（§4.3 的正确性依赖它）。
4. 规则拆分：N 个入站 → N 条规则，`InboundIds` 为空数组时按启用入站升序展开；
   block 动作不拆。
5. 克隆出站：深拷贝而非引用（改动克隆结果不影响原出站）；`direct` 动作克隆的是
   `tagDefaultOutbound` 的返回值而不是硬编码 tag。
6. 总开关关闭时，`GetXrayConfig()` 的输出与改动前**逐字节相同**
   （这是「升级后行为零变化」的唯一可验证形式）。
7. `RoutingRuleService.Del` 连带删除计量数据；`PruneOrphans` 兜底。
8. `ParseMeterTag` 对三种形态的反查，以及 `RecordMetered` 对 B 类 tag 的归因。
9. **热应用**：开关切换会一次增删约 82 个出站 + 替换整段路由。必须验证
   `tryHotApply` 能扛住这个批量（每个出站一次 RPC），失败会退回整进程重启——
   那正是本期要避免的。
10. **迁移**：拿一个真实的旧 traffic 库验证 `AutoMigrate` 之后新列与新索引都在
   （§6.1 的风险）。
11. **e2e（真实 xray）**：开关打开后配置能通过 `run -test`；IPv6 计量 tag 被接受
   （§4.4 的未验证假设）；分流结果不变
   （访问 ChatGPT 组的域名仍从 IProyal 出去）——这一条是 §5.5 那个风险的唯一防线，
   参照 `meter_rule_e2e_test.go` 与 `xray_hot_reload_e2e_test.go` 的写法。

## 11. 明确不解决的问题

### 11.1 被 block 的流量拿不到字节（有源码依据，不要再试）

管理员的直觉是对的：客户端确实把数据传到了服务器，这段流量真实发生过。
但它统计不出来，原因在 blackhole 的实现里：

```go
// proxy/blackhole/blackhole.go, func (h *Handler) Process
defer common.Interrupt(link.Writer)
defer common.Interrupt(link.Reader)   // TCP：直接中断读取，不消费上行数据
```

而出站计数器是包在 `Dial` 返回的连接上的（`app/proxyman/outbound/handler.go:356`
的 `getStatCouterConnection`）——**blackhole 根本不调用 `Dial`**，它没有对外连接，
所以那个计数器从来没被装上，恒为 0。UDP 分支会 `buf.Copy(link.Reader, buf.Discard, ...)`
排空数据，同样不经过计数器。

**这些字节没有丢**：它们已经在入站计数器（`inbounds.up`）里，因此流量配额、
到期判定、计费全都是准确的。缺的只是「把这部分单独摘出来标上名字」的能力。

**唯一能拿到它的做法是不用 blackhole**：改成 freedom 出站连一个本地丢弃端口，
这样就会经过 `Dial`、有计数器。**本期明确拒绝这条路**——它把「立即拒绝」变成
「建连再丢」，为一个统计数字给每条被封禁的连接引入一条新的失败路径
（本地端口不通、连接数放大、超时行为改变），代价与收益完全不成比例。

UI 上这一行只能是「N 次连接，字节数不可得」。

### 11.2 其余不解决的问题

1. **入站计数器没有按目标的维度**，所以上面那部分无法从入站侧反推。
2. **入站与出站的口径差 3~8%。** 前者是 VMess+WS+TLS 封装后的加密流，
   后者是解封装后的明文流。榜单加总永远小于首页数字，UI 继续标「约」。
3. **长尾域名仍在池外。** 见 §2.1，扩池的收益/成本比不成立。
4. **IP 行会吸进解析到该 IP 的域名流量。** 见 §4.3，xray 无条件可区分。
5. **热应用失败静默。** 见 §2.3 的附带发现，单独修。
